# ESP32-HAM-CLOCK: service layer, data model, memory, tasks

All line numbers refer to `src/ESP32-HAM-CLOCK.cpp` (18,615 lines). Toolchain: platformio/espressif32@6.12.0 (Arduino core 2.0.17), ArduinoJson 7.4.3, TFT_eSPI, XPT2046. Config persists in NVS namespace `"dxcluster"` (loadPreferences 16529+, save ~16750-16830).

## 0. Build result (pio run -e esp32-2432s028, SUCCESS, 36 s)

```
RAM:   26.3% (used 86304 / 327680 bytes)      static only: .dram0.data 26888 + .dram0.bss 59416
Flash: 90.4% (used 1303553 / 1441792 bytes)   app slot is 0x160000; .flash.text 974407, .flash.rodata 213652, .iram0.text 87579
```
- Flash is the binding constraint: only ~138 KB headroom in the app slot. LVGL core + widgets + fonts typically costs 150-300 KB, so the migration needs savings elsewhere (drop TFT_eSPI smooth-font code, drop dead code, move to a single-OTA or larger-app partition, `-Os`/LTO).
- Partitions (partitions_4mb_ota_1600k.csv): nvs 20K, otadata 8K, app0 1.4M, app1 1.4M, LittleFS ("spiffs") 0x130000 = 1.19 MB.
- LittleFS payload `data/` = 1.1 MB (about 93% of that partition): web UI (index.html, indexEN.html, style*.css), `fonts/Roboto10/12/20.vlw` (120K), `icon50/` weather icons (244K), logo.bmp, manuals. The web UI is served from LittleFS (`streamLittleFsFile("/index.html")`, 16947), not embedded in flash.
- Static RAM is small because nearly everything lives on the heap (String members, sprite, JSON docs).

### Service dependency notes
- Almost every service reads `getServiceCoordinatesForServices` (3552): GPS fix (if useGpsIfActive) > userLat/userLon > locator-derived.
- QRZ has a hidden UI dependency (current screen sets poll rate, 1362); `updateSpotsWithQrz` calls `updateScreen2/7` which are only flag setters (11622-11636), so that part is thread-safe.
- Time sources: GPS RMC (syncSystemTimeFromGps) preferred, NTP fallback; loss of GPS forces an NTP refresh (18250).
- Alerts are decoupled from the UI by flags + `portMUX` (11589-11620, 15059, 15879), which is a good seam to keep.

## 2. Data model

Arduino `String` on core 2.0.17 is 12 bytes (char*, capacity, len); heap block per String = capacity+1 rounded to 4 plus ~8 bytes allocator header (multi_heap). Estimates assume typical text; "worst" uses the clamp lengths (compact*Strings 1388-1425).

### Structs (all at file scope, forward declared 21-27)
- `DXSpot` (1255): String time, spotter, callsign; float frequency (kHz); String comment; float distance (km); String country, locator; float lat, lon; bool hasLatLon; String band, mode. 8 Strings, 4 floats, 1 bool = ~116 B static. Clamps: time 24, call 16, spotter 16, comment 96, country 28, locator 8, band 12, mode 8.
- `APRSStation` (1272): String time, callsign, symbol, symbolTable; float lat, lon; String comment; float freqMHz, distance; bool hasLatLon. 5 Strings, 4 floats, 1 bool = ~80 B. Clamps: time 24, call 16, symbol 12, comment 96.
- `AprsWxDecoded` (11870): hasAny; hasWindDir/windDirDeg(int); hasWindSpeed/windSpeedKmh(float); hasTempC/tempC; hasHumidity/humidityPct(int); hasPressure/pressureHpa(float). POD, ~44 B. Plain data, ideal for a shared header.
- `PropagationData` (1292): Strings sfi, kindex, aindex, muf, updated; hfBandLabel[4], hfBandFreq[4], hfBandDay[4], hfBandNight[4] (16 Strings); bool valid; String lastError; ulong fetchedAtMs. 22 Strings = ~280 B static, ~400 B heap.
- `WeatherData` (1311): Strings cityName, description, iconCode, forecast3hDesc, forecastNextDayDesc, forecastError, updated, lastError, detailIconCode[5]; int weatherId; float tempC, windMs, pm25, pm10; int humidity, pressure; float forecast3hTempC/WindMs + bool valid; same for forecastNextDay; DETAIL_COLS=5 arrays tempC/humidity/windMs/weatherId/valid; nightTempC[2]/nightTempValid[2]; bool valid; ulong fetchedAtMs. ~300 B static plus ~250 B heap (reserve() calls in setup 18104-18111).
- `WeatherAlertInfo` (1627): bool stormPossible, stormNow, windPossible; uint8 stormEtaHours (actually the repeat minutes); float maxWindMs, maxWindGustMs. POD 16 B.
- `PendingQrzLookup` (1351): String callsign, ulong nextTryMs, uint8 attempts (~20 B).
- `QrzCacheEntry` (2445): String callsign, grid, country; float lat, lon; bool hasLatLon; ulong fetchedAtMs (~56 B).
- `AprsAlertCooldownEntry` (1658): String callsign; ulong lastAlertMs (16 B).
- `BridgeBtDevice` (1757): String name, addressNoColon (24 B).
- `TftUiPalette` (846), `MatrixDrop` (4408): UI only. Enums: ScreenType (533), TftLang, TftStyleMode, DxTableSizeMode, Screen2FilterMode, Screen6SortMode, Screen6ViewMode, AlertScreenKind (1620), TrKey (908, i18n key table).

### Biggest RAM consumers (runtime)
1. **Shared table sprite**: `sharedTableSprite` 320 x (220-32=188) x 16 bpp = **120,320 B** of contiguous heap (737-790, 5521, 5957, 8564), allocated lazily on first table screen. Biggest single block; with TLS handshakes it makes contiguity the main OOM risk. LVGL partial draw buffers (e.g. 320x20 x2 = 25 KB) replace it.
2. **mbedTLS handshake buffers** for each HTTPS fetch (about 40-50 KB contiguous transient): weather, forecast (up to 3 tries), air pollution, propagation, QRZ, POTA. All created/destroyed repeatedly in the loop task.
3. **JSON documents**: POTA API streamed doc hinted 60,000 (13831) and fallback 120,000 (13966-ish; full unfiltered). Forecast doc hint 28,672 (9707). With ArduinoJson 7.4.3 these `DynamicJsonDocument(n)`/`StaticJsonDocument<n>` are deprecated aliases of the elastic JsonDocument, so the number is not preallocated, but real use still scales with content (filtered POTA ~ tens of KB, unfiltered fallback can exceed free heap). Web handlers use `StaticJsonDocument<12000>` for 4 of the endpoints (16954, 17004, 17030...). HamAlert doc 3072 per line (14316).
4. **Spot arrays** (about 32 KB DX, about 10 KB each POTA/HamAlert).
5. **Propagation XML payload** as one String (hamqsl solarxml is a few KB), plus `http.getString()` in QRZ (a few KB per call).
6. LittleFS + TFT_eSPI smooth-font (.vlw) buffers per `loadFont` (warmupSmoothFonts, 881-901). Fonts reloaded on screen draws (4722, 10330, 12446).
7. FreeRTOS: loop task stack 8 KB + UI task stack 8 KB, WiFi/lwIP.

### Heap-fragmentation hot paths (String churn)
- `addSpot` (14256), `addPotaSpot`, `addHamalertSpot`, `addAPRSStation` (15807): insert at index 0 by shifting the whole array with `spots[i] = spots[i-1]` (100 DXSpot copy-assignments, about 800 String assignments per incoming spot, each possibly realloc) while holding the mutex. Replace with a ring buffer / index.
- `fetchPotaApi`: builds up to 30 DXSpot from JSON, O(n^2) sort with DXSpot swap via temp copy (13866+), String `>` compares.
- `parseDXSpot` (14040): chain of `substring()`, plus a per-character `substring(i,i+6)` locator scan over the comment (up to 96 allocations). `parseAPRSFrame`/`parseAprsAdvancedPosition` also allocate several substrings/Strings per frame at APRS-IS rates (r/50 km filter can be many frames per second in cities).
- `handleAPRSData`: per-char `aprsBuffer += c`, then `String line = aprsBuffer` copy, `processAprsFrameFromLine(const String&)`, then `APRSStation` by value into `addAPRSStation(APRSStation)` and again into `aprsAlertPendingStation`.
- `shouldTriggerAprsAlert` splits the CSV watch list with `substring` and sanitizes tokens for EVERY received frame, per token.
- `enqueueQrzLookup/isQrzQueued` copy and uppercase Strings for each queue entry.
- `fetchPropagationData` and QRZ: `getString()` of whole bodies; `extractXmlTagValue` returns Strings.
- Telnet: `pendingTelnetLine = telnetBuffer` then `String line = pendingTelnetLine` copies.
- Critical-section copies: `aprsAlertPendingStation = station` (15879) and `weatherAlertPendingInfo` (15060) happen inside `portENTER_CRITICAL`; the APRSStation copy allocates Strings with interrupts/other core blocked (WeatherAlertInfo is POD, fine).

## 3. Tasks and concurrency

- Only ONE explicit task: `xTaskCreatePinnedToCore(uiTaskLoop, "UI_Task", 8192, nullptr, 2, &uiTaskHandle, 1)` at setup end (18212-18220), guarded by `ENABLE_TFT_DISPLAY`. Stack 8192 bytes, priority 2, **core 1**.
- Arduino `loopTask` (setup + loop) runs on **core 1**, priority 1, default 8 KB stack (no SET_LOOP_TASK_STACK_SIZE override found). Both app tasks therefore share core 1; core 0 holds WiFi/lwIP/bt stack.
- `setup()` (18060-18220): Serial, create 4 mutexes (18085-18096), RGB LED, TFT init, LittleFS, loadPreferences, `reserve()` String buffers, configureUart2Port, WiFi connect (blocking, falls to AP), updateNTPTime, connectToCluster, setupWebServer, splash screens with delays (about 7 s: 4000+3000 ms), warmup fonts, then start UI task. UI task starts only after setup completes.
- `loop()` (18225-18615), sequential, ends with `delay(10)`: pollGpsSerial, bridge/TNC boot services, GPS time sync, deferred restart, `server->handleClient()`, NTP, WiFi state, RGB LED, WiFi retries, DX telnet read, POTA/HamAlert polls, APRS-IS read/watchdog/filter, beacon TX, propagation, QRZ queue (1 per pass), weather, backlight day/night check (5 min, 631), weather alert scheduler, parse 1 pending DX line, parse 1 pending POTA line (dead producer), telnet watchdogs, login scheduling, keepalives.
- `uiTaskLoop()` (17890-18056), `vTaskDelay(10 ms)`: consumes redraw flags (uiPending* under `uiPendingRedrawMux` portMUX), draws screens, pops alert flags (`aprsAlertDrawPending`, `weatherAlertDrawPending`), `updateAlertScreenTimeout`, `handleTouchNavigation`, auto-switch timer, periodic per-screen update functions (1 s clock, 100-200 ms tables, matrix/Unlis games every frame). All TFT and touch access lives here.
- Shared state / sync primitives:
  - Mutexes (SemaphoreHandle_t, `portMAX_DELAY`, null-safe wrappers 1427-1473): `dxSpotsMutex`, `potaSpotsMutex`, `hamalertSpotsMutex`, `weatherDataMutex`.
  - `portMUX_TYPE`: `uiPendingRedrawMux`, `aprsAlertPendingMux`, `weatherAlertPendingMux`.
  - `volatile bool` flags: aprsAlertDrawPending, weatherAlertDrawPending, uiPending*.
  - **Unprotected shared data**: `aprsStations[]`/`aprsStationCount` (written in loop, read by UI draw and web /api/aprs), `propagationData`, `qrzStatus`, `qrzCache`, gps* globals (written in loop, read by UI), `currentScreen`/`inMenu` (written by UI, read in loop via getQrzLookupIntervalMs), `aprsAlertScreenActive`.
  - **No TFT/SPI mutex.** The loop task draws on the TFT directly in at least `APRS_BEACONING_Screen` (12520, called from sendAprsPositionToKiss in loop task) and bootLogLine (before UI task exists, fine), so KISS beaconing races the UI task for the SPI bus.
  - `alert` popup calls such as `ALERT_Screen` are called from the UI task (OK).
- Blocking in the loop task (affects everything above because it is one thread):
  - fetchHamalertTelnet: up to about 1.2 s pre-login + delays + 9 s read, every 60 s.
  - HTTPClient timeouts 8 s (POTA, propagation, weather, forecast up to 3 tries at 8-12 s), QRZ 3 s per call (and QRZ session login another 3 s).
  - connectToAPRS: `delay(500)` x2; sendClusterConfigCommands: `delay(500)` + `delay(50)` per command.
  - connectToWiFiWithAttempts: up to 20 s per SSID (called also from loop retries with 6-ish attempts).
  - During these, `pollGpsSerial` and `handleTelnetData`/`handleAPRSData` are not drained: UART2 RX buffer (HardwareSerial default 256 B, hardware FIFO 128 B) overflows in about 0.27 s at 9600 baud, so GPS NMEA and KISS/TNC frames are lost during every fetch; TCP data is buffered by lwIP but the single-slot `pendingTelnetLine` drops lines.
  - Web server runs in the same loop task, so the config UI freezes during fetches.

## 4. Surprises and risks (for the migration spec)

1. Flash at 90.4% of the app slot (138 KB headroom) is the real blocker for LVGL; RAM is not (26% static), but heap contiguity is.
2. 120 KB sprite plus 45 KB TLS buffers share the ~200 KB runtime heap.
3. POTA telnet path is dead code: `handlePotaTelnetData` is never called (only defined 16445 and declared 478), yet `connectToPotaCluster` is still called in setup and loop and has a 5-min watchdog. POTA actually comes from the HTTP API.
4. HamAlert is "poll by reconnecting" every 60 s (new login each time); it resets `hamalertSpotCount = 0` before reading, so a failed poll empties the screen.
5. No DST/IANA TZ: timezone is a float hour offset only (16579, 4520).
6. TFT drawn from the loop task (APRS_BEACONING_Screen) with no SPI lock.
7. Three shared structures lack locks (aprsStations, propagationData, gps*).
8. Everything blocks one thread; GPS/KISS bytes are dropped during fetches.
9. Security: all TLS is `setInsecure()` or default HTTPClient (no CA pinning); QRZ username/password and OWM key travel in URL query strings; default AP password `1234567890` hard-coded; `/api/save` and `/api/config` expose and accept QRZ/APRS/WiFi passwords in clear JSON (17798 area) with no auth observed.
10. Mixed-language comments/strings (Polish/Portuguese remnants such as "ekranie POTA", "pt_br" weather language) and `WEATHER_ALERT_*_TEST_MODE` leftover flags (const false).
11. Dead/incomplete: `DEFAULT_APRS_PASSCODE 00000` (octal literal, equals 0) means unverified login by default.
12. `stormEtaHours` field of WeatherAlertInfo actually carries repeat minutes (15149).
13. Duplicate declarations: `extractXmlTagValue` exists with two signatures (277 static const char*, 398 String tag, 13382).
