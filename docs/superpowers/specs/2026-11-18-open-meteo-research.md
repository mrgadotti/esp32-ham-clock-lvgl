# Open-Meteo research (fetched 2026-11-18)
## 1. Free-tier limits
- https://open-meteo.com/en/pricing: "600 calls / min", "5.000 calls / hour", "10.000 calls / day", "300.000 calls / month" (FAQ: "monthly limits are not enforced" until available).
- https://open-meteo.com/en/terms: "Less than 10'000 API calls per day, 5'000 per hour and 600 per minute." Scope: "Rate limits are applied by IP addresses and application." (per IP; no API key on free tier; not per account).
- Non-commercial: "You may only use the free API services for non-commercial purposes." (terms); pricing: "The free API is for non-commercial use."
- Attribution: "The data obtained through the API is provided under the terms of the CC-BY 4.0 licence." Docs footer suggests "Weather data by Open-Meteo.com" style credit (docs: "Source: Open-Meteo"). Exact mandated string not given; credit + link is enough. Air quality: must credit CAMS (Copernicus Atmosphere Monitoring Service ADS) plus Open-Meteo.
- Live headers show WEIGHTED cost: X-RateLimit-Limit: 600.0, X-RateLimit-Window: 60, X-RateLimit-Cost: 1.8 for the request below (cost grows with variables x days), 1.0 for a trivial request, 0.0 for HTTP 400/redirect-less probe.
## 2. Exceeding the limit
- Official docs only document HTTP 400 with {"reason":"...","error":true}. 429 not documented in primary pages.
- Secondhand (GitHub issues, e.g. https://github.com/cyanheads/open-meteo-mcp-server/issues/75): HTTP 429, body {"error":true,"reason":"Too many concurrent requests"} (5 in flight per IP) or minute/hour/day-limit reason. Retry-After inconsistent/often absent; do not rely on it (use fallback backoff, e.g. 60 s+).
## 3. Minimal ESP32 request (verified 200)
https://api.open-meteo.com/v1/forecast?latitude=-23.55&longitude=-46.63&current=temperature_2m,apparent_temperature,relative_humidity_2m,surface_pressure,wind_speed_10m,wind_direction_10m,wind_gusts_10m,weather_code,is_day,cloud_cover,visibility,uv_index&daily=weather_code,temperature_2m_max,temperature_2m_min,precipitation_probability_max,sunrise,sunset&timezone=auto&forecast_days=5&wind_speed_unit=kmh
- `current=` is the new interface (15-min data, "interval":900); `current_weather=true` still works (verified) but returns only temp/wind/code/is_day with different key names (temperature, windspeed, weathercode). Use current=.
- Size: 1483 bytes plain, 619 bytes gzip (Accept-Encoding: gzip; server sends gzip, Content-Length 20 on a HEAD-like probe is irrelevant). Plain is chunked (no Content-Length); gzip response has Content-Length. ESP32 HTTPClient lacks gzip decode -> expect ~1.5 KB plain; fine for ArduinoJson (~3 KB doc).
- Note: sunrise/sunset in daily are local time with timezone=auto; no hourly needed. Add `&timeformat=unixtime` to shrink further if desired.
- Sample (lat -23.55, lon -46.63; snapped to -23.514938,-46.610504):

## 6. HTTPS / TLS
- Plain HTTP works: curl http://api.open-meteo.com/v1/forecast returned 200 (no redirect), so ESP32 can use HTTP (no cert handling). HTTPS not mandated by terms.
- TLS chain (openssl s_client): leaf CN=*.open-meteo.com <- Let's Encrypt CN=YE1 <- ISRG "Root YE" <- ISRG Root X2 <- ISRG Root X1 (self-signed anchor, via cross-signs). Pin ISRG Root X1 (or X2) as root CA; the new LE chain is ECDSA, so mbedTLS needs ECDSA support (the ESP32 Arduino bundle has it). Not documented by Open-Meteo; observed 2026-11-18, may rotate.
## 7. Update cadence
- Docs: "Current conditions are based on 15-minutely weather model data."; model cadences "Every hour"/"Every 3 hours"; outside regions with native 15-min data "data is interpolated from 1-hourly to 15-minutely". Response "interval":900 s. So 10-min polling is useless-ish; 15 min matches (30 min is plenty for a clock). Unchecked: per-model detail at /en/docs/model-updates.
